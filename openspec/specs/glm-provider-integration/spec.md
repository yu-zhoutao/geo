## Purpose
Define the application-managed model provider boundary and the first GLM-5 integration for app-owned model tasks and backend-managed OpenCode runtime sessions.

## Requirements

### Requirement: Application-managed model provider boundary
The backend SHALL expose a small application-managed model provider boundary for app-owned GLM model tasks and backend-managed OpenCode runtime provider selection, and the user-facing environment configuration for that boundary SHALL include GLM settings plus explicit runtime-provider selection settings.

#### Scenario: Provider is configured through app-managed settings
- **WHEN** the application starts with required model configuration available for the selected runtime provider
- **THEN** the backend initializes provider configuration through application-managed settings rather than requiring the user to wire model configuration through external runtime files
- **AND** GLM API key and bare GLM model name remain the default user-facing model settings

### Requirement: GLM-5 is supported as the default provider
The system SHALL support `bigmodel.cn` GLM-5 as the default provider for app-owned model tasks and backend-managed OpenCode runtime sessions, with `glm-5.1` as the default GLM model and with GLM model settings represented as bare GLM model names such as `glm-5`.

#### Scenario: GLM-5 provider can be initialized
- **WHEN** valid GLM provider credentials are available in the environment and GLM is selected
- **THEN** the backend can initialize a GLM-5 client for application-managed requests and managed OpenCode runtime sessions without requiring users to patch source code or provide ad hoc runtime config files

#### Scenario: Bare GLM model name is accepted
- **WHEN** `GEO_AGENT_GLM_MODEL` is set to a valid bare GLM model name such as `glm-5`
- **THEN** app-owned GLM model tasks receive that exact bare model name
- **AND** backend-managed OpenCode runtime config derives its provider-qualified GLM runtime model from that bare model name when GLM is selected

#### Scenario: Provider-qualified model name is rejected
- **WHEN** `GEO_AGENT_GLM_MODEL` is set to a provider-qualified value such as `zai/glm-5` or `zhipuai/glm-5`
- **THEN** settings validation fails instead of silently rewriting the model name for compatibility

### Requirement: Session titles can be generated by the configured model
The backend SHALL treat application-managed model title generation as a fallback capability for session naming rather than the primary title source, and SHALL prefer runtime-derived session titles whenever the managed OpenCode session exposes a usable title.

#### Scenario: Runtime title is preferred when available
- **WHEN** a managed OpenCode session exposes a runtime-derived title for the current conversation
- **THEN** the backend uses that runtime title as the visible session title instead of generating a separate app-owned model title for the same session

#### Scenario: Auto-title fallback is generated only when runtime title is unavailable
- **WHEN** a user creates a session and the managed runtime does not expose a usable session title after the initial request
- **THEN** the backend may keep the fallback title or generate a provider-backed fallback title asynchronously without blocking normal session execution

#### Scenario: Provider failure does not block session creation
- **WHEN** model-backed fallback title generation fails or times out
- **THEN** the session remains usable with its existing fallback title and the failure does not prevent normal session creation

### Requirement: Agent runtime uses the configured provider
The backend SHALL use the application-managed provider configuration when provisioning OpenCode runtime config and auth instead of requiring separate user-authored provider wiring, and SHALL derive OpenCode's provider-qualified model identifier from the selected provider and validated provider-specific model setting.

#### Scenario: GLM runtime inherits configured model settings
- **WHEN** the backend starts or reconfigures the managed OpenCode runtime with GLM selected
- **THEN** the runtime receives `zhipuai` provider, GLM model, and GLM auth settings derived from the application-managed provider boundary
- **AND** model configuration is generated without `zai` to `zhipuai` compatibility rewriting

#### Scenario: DeepSeek runtime inherits configured model settings
- **WHEN** the backend starts or reconfigures the managed OpenCode runtime with DeepSeek selected
- **THEN** the runtime receives `deepseek` provider, DeepSeek model, and DeepSeek auth settings derived from the application-managed provider boundary
- **AND** the generated OpenCode model identifier is `deepseek/<deepseek_model>`

#### Scenario: Built-in DeepSeek provider is used without custom provider metadata
- **WHEN** the backend generates OpenCode runtime config with DeepSeek selected
- **THEN** it enables OpenCode's built-in `deepseek` provider
- **AND** it does not write a custom DeepSeek provider block, base URL, endpoint schema, or model catalog into the generated config

#### Scenario: Provider failure blocks real agent execution explicitly
- **WHEN** the selected provider cannot be initialized or provisioned for the OpenCode runtime
- **THEN** the backend reports a not-ready runtime state for agent execution instead of silently falling back to simulated session behavior

### Requirement: Provider secrets remain external to persisted session metadata
The backend MUST keep provider credentials in environment-managed configuration and MUST NOT persist raw model API keys in SQLite session records, workspace files, or bundled runtime manifests.

#### Scenario: Session metadata excludes secrets
- **WHEN** session metadata is persisted or indexed locally
- **THEN** it contains provider references or status only as needed and does not store raw provider credentials
